# device-test

```
ticket + diff → test plan → runner → scenario runs whole → verdict table
```

Driving a phone tap by tap costs one round trip per tap, each re-reading the whole context. Here a scenario is a
Python file that `devtest run` executes in one Bash call, printing about ten lines. The engine refuses to pass what
it did not look at: every criterion is covered or skipped with a reason, an absence counts only if the same thing is
seen present in the run, a check the phone cannot observe is `N/A`, never PASS, and a failure caused by the phone
(it dropped off, another app took the front, the log capture died) is BLOCKED, never blamed on the app.

The tool is `python3 ~/.claude/skills/device-test/scripts/devtest.py --owner NAME …` (standard library only; `--help`
lists every command). Talk to the user in their language; plans, scenarios and reports to the runner are in English.

## Engine and pack

The engine here knows no app. Everything about one app is a **pack**, a folder `packs/<name>/` next to `scripts/`
(gitignored: it holds phone ids and paths, so it stays local):

| | |
|---|---|
| `pack.json` | the app's constants: `android` (`package`, `activity`, `build`, `apk`, `prefs`, `db`, `permissions`), `ios` (`bundle_id`, `team_id`, `scheme`, `project`, `prefs`, `db`), `phones` (`alias → {platform, id, name}`), `default_for`, `launch` (environment screen, prompts to dismiss, login screen, `screen_tags`), `state_dir`, `notifier`, `guard` (strings file, source globs, flow modules) |
| `flows/` | the app's shared flows (`nav.py`, `tags.py` with every selector, `logs.py` with every log pattern), merged into the engine's `flows` package; `API.md` is generated by `devtest api` |
| `scenarios/`, `suites/` | the scenario files and the regression suites |
| `hooks.py` | what is code, not a constant: `override_key(top, name)` for feature flags, `clean(x, prefix)`, `ios_airplane` / `ios_metered` (the app's own log line that confirms a hand action), `tags_check`, `pref_key` |
| `runner.md` | the app's and the phones' own quirks, read by the runner after the engine's `runner.md` |

The pack is the one `device_test.pack` names in the project's `.claude/config/project.json` (a name under `packs/`,
or an absolute path), otherwise the only pack under `packs/`; the rest of that `device_test` block overrides
`pack.json` key by key. With no pack the engine still runs (`devices`, leases, `lint`) and says which key a command
misses. `examples/open-app.py` is a scenario that needs only the app's id.

Phones: Android needs `adb` and USB debugging; the iPhone needs Xcode, Developer Mode, a paired phone, the pack's
`ios.team_id` with a local provisioning profile, and WebDriverAgent's sources (the engine says the `npm` command
when they are missing). adb, usbmuxd and `devicectl` need the USB devices: under Claude Code's Bash sandbox, add the
devtest command to `sandbox.excludedCommands`.

## Rules

1. **The main session does not drive phones and does not run scenarios.** Writing, running and rerunning a scenario,
   the red proof and a regression suite go to the runner, with the plan below.
2. **Who the runner is.** By default the `device-tester` agent (`dev:device-tester` from the plugin), launched in
   the background with the plan as its prompt. First print this skill's section of the project's playbook with
   `python3 "${CLAUDE_SKILL_DIR}/../../shared/project_config.py" section device-test`: where it names another runner
   (Codex through sub-codex, say) or other rules, the section wins.
3. The main session may run the read-only commands itself: `devices [--json]`, `lease status`, `build-info`,
   `suite report NAME`, `lint`. `build-info` waits for a phone that is not plugged in: give that Bash call a timeout
   above 300000.
4. A phone leased by another session: ask the user before taking it; the runner never forces a lease. A phone that
   is not connected: devtest posts a notification asking to plug it in (the pack's `notifier`) and waits up to
   5 min (`DEVTEST_PLUG_WAIT`, `0` fails at once).
5. Hand actions (plugging in, a network switch on iOS) are asked through the pack's notifier, never assumed.

## Test plan (main session → runner)

The runner gets exactly what to test, so it neither invents checks nor drops them. Write the plan from the ticket,
the diff and the intended behaviour, to a scratchpad file:

```
Ticket: <id> · <title>
Plan file: <absolute path of this file>
Worktree: <path under test> · red proof on: <base build or worktree | none>
Phones: <aliases> · owner: <runner>-<id>
Scenario: new <id>.py | existing <file> (run as is | extend with AC4)
Setup: account and environment, data to prepare, network state, flags
Checks (one per line, keep the IDs):
  AC1 <action> → <expected, with its evidence: screen tag or text, log line, pref, db row, file>
  AC2 …
Not to test: <what and why>
```

- Every check names its evidence. One a phone cannot observe is `N/A on ios (why)` or goes under "Not to test".
- The runner tests these checks and nothing else; it adds only the navigation and setup they need. A check it cannot
  do as written comes back BLOCKED with the reason, never swapped for another one.
- A rerun is a plan too: the scenario, phones, worktree, and the checks (`--only AC2,AC3`) if not all of them.
- Phones run side by side, never one after the other: the same checks on several phones are one plan (one
  `devtest run --device a,b` call); different checks per phone are one plan and one runner per phone, launched
  together.

## Report (runner → main session)

```
<id> · pixel PASS 8/8 · iphone FAIL step 3
AC1 PASS · AC2 FAIL (iphone: no log /…/ within 15s) · AC3 N/A on ios (why) · AC4 SKIP (why)
evidence: <state_dir>/runs/…/iphone/step-3.{png,ui.txt,log}
not tested: … (why)
scenario: <path> (new|changed|unchanged)
flows: <added or changed, or unchanged>
cleanup: <what the run created and deleted, or "nothing created">
```

Relay it to the user in their language. Open the evidence only for a FAIL whose line does not explain it. A report
without the `cleanup` line, or with something left behind, goes back to the runner for the cleanup first. Exit codes
of `run`: 0 PASS · 1 FAIL (the app) · 2 BLOCKED (phone, tooling, lease, stale build) · 3 SCENARIO ERROR.

## Run

Launch the runner once, in the background (runs often take more than five minutes), with the plan as its prompt.
The `device-tester` agent reads `runner.md` here and the pack's `runner.md` itself. Read the verdict table when it
ends.
